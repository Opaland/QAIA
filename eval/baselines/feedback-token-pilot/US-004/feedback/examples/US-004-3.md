# US-004-3 — negative scenarios must carry a machine-readable reason code

**Scenarios**: `@QAIA-US-004-012` and `@QAIA-US-004-013`
(`.qaia/testbooks/US-004/approval-chain.feature`, AC2-C5 and AC3-C1) — representative examples;
the same pattern applies to every `@negative` scenario in the book (17 total, see
`.qaia/testbooks/US-004/coverage-matrix.md`).

**Generated (as produced by `testbook-generate`)**:

```gherkin
Scenario: An approver acting out of chain order is refused
  Given a submitted report "R" by "employee@demo" totalling exactly 5000.01 EUR
  When "finance@demo" attempts to approve report "R" before the manager has
  Then the attempt is refused with a 403 status
```

```gherkin
Scenario: An approver cannot decide on their own report
  Given a submitted report "R" by "manager@demo" totalling exactly 499.99 EUR
  When "manager@demo" attempts to approve report "R"
  Then the attempt is refused with a 403 status
```

**What was wrong (tester correction, QA lead)**: a bare HTTP status is not enough to
automate a negative-path assertion or to distinguish this refusal from any other 403 in the
system in a test report or a monitoring dashboard. The team's Gherkin convention (used
elsewhere in the project, not yet reflected by `testbook-generate`'s output) requires every
refusal `Then` step to also assert a machine-readable reason code.

**Corrected form**:

```gherkin
Then the attempt is refused with a 403 status and reason code "APPROVAL_OUT_OF_ORDER"
```

```gherkin
Then the attempt is refused with a 403 status and reason code "SELF_APPROVAL_FORBIDDEN"
```

**Why**: wording/structure convention, not a domain rule — the *behavior* (403, refusal) is
unchanged, only the assertion granularity. Filed as `style`.

**Immediate promotion requested**: the user (QA lead, simulated) explicitly asked for this
convention to be promoted right away rather than waiting for a second recurrence, using the
skill's single-criterion promotion path ("the user explicitly asks for immediate promotion",
`SKILL.md` step 4) — the convention already applies project-wide by policy, waiting for a second
captured instance would just delay every other negative scenario regenerating without it.

**Provenance**: simulated correction, non-interactive pilot run (2026-07-25), `simulated:
accepted, immediate promotion requested` per `skills/README.md` rule 3.
