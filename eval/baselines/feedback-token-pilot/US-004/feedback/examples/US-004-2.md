# US-004-2 — stale FX fallback rate must be capped, not used indefinitely

**Scenarios**: `@QAIA-US-004-026` and `@QAIA-US-004-027`
(`.qaia/testbooks/US-004/approval-chain.feature`, AC6-C3 and AC6-C4)

**Generated (as produced by `testbook-generate`)**:

```gherkin
Scenario: An expense dated in a weekend rate gap uses the last available rate
  Given "employee@demo" has a draft report in "USD" with one line "hotel" of 100.00 dated 2026-07-25, receipt attached
  When "employee@demo" submits the report
  Then the report is flagged as using a stale exchange rate
  And the report's converted total is approximately 91.90 EUR
```

This resolved **Q4**'s fallback half with the default: "last available prior rate + `rateStale`
flag", with no bound on how far back that prior rate may be.

**What was wrong (tester correction, Finance SME review)**: an unbounded "last available rate"
fallback means a report submitted after a long outage (e.g., FX feed down for two weeks) could
silently use a two-week-old rate flagged only with a soft `rateStale` marker that approvers
routinely ignore. Actual Finance policy caps the fallback at **5 business days**: within the cap,
the flagged stale rate is used as generated; beyond the cap, the same `pending-rate` hold from
`US-004-1` applies instead of ever using a rate that old.

**Corrected form** (new scenario, in addition to keeping 026 as-is for the within-cap case):

```gherkin
Scenario: An expense whose last available rate is older than 5 business days is held for manual rate resolution
  Given "employee@demo" has a draft report in "USD" with one line "hotel" of 100.00 dated 2026-07-25, receipt attached
  And the last available USD rate is 7 business days old
  When "employee@demo" submits the report
  Then report "R" status is "pending-rate"
  And the report does not enter any approver's queue
```

Scenario `@QAIA-US-004-027` (the triple AC2×AC3×AC6 intersection) also needs a sibling case for
the beyond-cap path once regenerated, since it currently assumes the stale-rate branch always
proceeds.

**Why**: same underlying policy as `US-004-1` — unresolved/stale FX data routes to
`pending-rate`, never a silent old value or a hard refusal. Two independent scenarios now carry
this pattern (`US-004-1`, `US-004-2`), meeting the ≥ 2 recurrence threshold for promotion (D22).

**Provenance**: simulated correction, non-interactive pilot run (2026-07-25), `simulated:
accepted` per `skills/README.md` rule 3 — see `US-004-1` for the same caveat.
