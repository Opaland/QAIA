# QAIA — where the project actually stands

*English summary, last updated 8 August 2026. The full record is [`STATUS.md`](STATUS.md) and
[`DECISIONS.md`](DECISIONS.md) — both in French, both far more detailed than this page. This
document exists because the project's credibility rests on documents an English reader could not
read, which is a strange way to ask for trust.*

---

## One paragraph

QAIA is **pre-alpha**. Four Claude Code plugins, 30 Markdown skills, MIT. It takes a user story
to a traceable Gherkin test book and then to native Playwright tests. It has never been run
end to end by a QA engineer on their own work, so the only honest answer to *"does it help?"* is
**unknown**. What follows separates what has been demonstrated from what has not, and the second
list is longer.

## What is demonstrated

| Claim | Evidence you can open |
|---|---|
| A suite generated by QAIA runs **without QAIA** — no Claude session, no skill loaded | [CI run 30702503888](https://github.com/QAIA-Project/QAIA/actions/runs/30702503888), 8 tests, 8 green; raw log in `eval/ci-proof-2026-08-01/` |
| One user story → 38 scenarios, each traced to an acceptance criterion, 11 flagged with a named open question | [`examples/expense-demo/qaia-journey/`](../examples/expense-demo/qaia-journey) — the whole run, checkpoints included |
| Two independent domains taken end to end | `examples/expense-demo/` (finance/HR, 43 green tests) and `examples/medibook/` (healthcare-shaped, 32 green tests) |
| Every manifest in the repository validates, enforced in CI | 32 manifests, `eval/tools/validate_manifest.py`, CI job |
| The scorer is a different component from the producer | [`plugins/qaia-score/`](../plugins/qaia-score) — read-only, separate plugin |
| Real defects found by the skills, on real targets | An IDOR on `GET /api/audit` (found and fixed same day); a numeric-overflow contract break, `CP-001`, in `eval/contract-probe-2026-08-01/` |

## What is not demonstrated — the part that matters

1. **No human pilot, ever.** Every measurement of QAIA was produced by evaluation harnesses, CI,
   or agent panels. None by a tester doing their job. This is the project's largest unknown and
   nothing internal substitutes for it. There is a [15-minute pilot kit](PILOT-KIT.md) if you
   want to be the first.
2. **The reviews are self-administered.** A 13-persona review scored QAIA **2.4/5** and an
   architecture review scored it **5.0/10**. Both are published with what was fixed and what was
   not — and **both were run by this project on itself**, agent panels playing a fictional review
   firm. That is a hostile-reading exercise, which has value, but it is not independent
   validation and must never be described as an external audit.
3. **Against a plain direct prompt, the result is mixed.** Measured on the same ticket
   ([benchmark](../eval/baselines/qaia-vs-direct-prompt-benchmark-2026-07-28.md), N=1 per arm):
   QAIA cost **~2.9× more tokens** (133,100 vs 46,548); it scored better structurally on average
   (72 vs 47/100) but still failed the structural gate on 2 of 7 files; and **the direct prompt
   matched or slightly beat it on strict recall of the planted ambiguities**. The one clean
   separation: the direct prompt silently invented four business rules and folded them in; the
   QAIA arm invented none and traced every assumption to a numbered question. The value
   proposition this supports is *structure and verifiability at roughly triple the cost* — not
   "finds more".
4. **The quality of the output for a real user is unmeasured.** Structural scores and mutation
   runs say the assertions are load-bearing. They say nothing about whether the scenarios are the
   *right* ones for your product.
5. **No regulatory framework is mapped.** The healthcare example demonstrates traceability on a
   healthcare-*shaped* domain. It maps neither IEC 62304, nor 21 CFR Part 11, nor ISO 13485. The
   original "medical software" positioning was retired for exactly this reason.
6. **Zero adoption.** At the time of writing: no stars, no forks, single-digit unique visitors.

## Things the project got wrong and fixed, because that list is also evidence

- A CI job was written for the *instance* of a bug rather than its *class*, and missed two
  defects that were in the validation tool itself — a validator can be wrong by refusing a state
  the contract allows, and that failure never raises an alert.
- The `contract-probe` skill's first run against its own demo app **tested nothing**: seven
  probes hit an endpoint that silently ignored their payload and all returned the same plausible
  422. Written up as-is it would have reported six promises as kept without exercising one.
- The generated suite for one story asserted only that an error was *visible* where the
  requirement demanded a *generic* message — so it passed against the very user-enumeration
  defect the word "generic" exists to forbid. **The weakness was in the specification first; the
  code inherited it.**
- This project's own landing page, written on 8 August 2026, advertised a coverage gate that had
  been replaced eight months earlier, dropped a word from a quote it called verbatim, and
  asserted things about competitors that their documentation does not support. A five-lens review
  panel caught all of it within hours of publication. See D141.

## How to judge this project in ten minutes

Open [the CI run](https://github.com/QAIA-Project/QAIA/actions/runs/30702503888) — that is the
one claim no marketing can fake. Then open
[`examples/expense-demo/qaia-journey/testbooks/US-004/coverage-matrix.md`](../examples/expense-demo/qaia-journey/testbooks/US-004/coverage-matrix.md)
and look at the rows marked **low (Q1)**, **low (Q2)** — decide for yourself whether a tool that
refuses to resolve an ambiguity is useful to you or merely slower. Then read the
[benchmark that goes against us](../eval/baselines/qaia-vs-direct-prompt-benchmark-2026-07-28.md).

If you conclude it is not worth your time, that is a legitimate conclusion and this page was
written to let you reach it quickly.
